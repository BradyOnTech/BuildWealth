BuildWealth SaaS Plan

Transition from local single-user app to privacy-first hosted SaaS.

This plan assumes a B2C-first product for normal people managing their financial life, with an architecture that can later support advisors and small firms without starting over. The initial target is tiny: 1 to 9 real users, no existing production obligations, and freedom to reshape the system now while the blast radius is still mercifully small.

1. North Star

Do not turn BuildWealth into a generic multi-tenant dashboard. Turn it into a hosted private financial workspace that feels as safe and personal as the local app, but can be reached from a browser and operated by normal users.

Strategic Choice
Positioning

Use "financial operating system" language before "advisor" language.

The product can help users organize, model, review, and understand their finances. Any language implying personalized investment, tax, legal, or fiduciary advice should be reviewed before launch.

Architecture

Adopt a private-workspace SaaS model.

Each household or organization receives an isolated workspace. For the first 1-9 users, this can be one SQLite database per workspace plus a small control-plane database for login, billing, and routing.

Scale

Optimize for correctness, isolation, and iteration before raw throughput.

The first hosted version should survive real users and real sensitive data. It does not need sharding, Kubernetes, or a shared relational fleet on day one.

Future

Model organizations now, even if only households use it first.

A household is just an organization with one owner and maybe family members. This keeps the advisor/firm path open without burdening the first B2C release.

SQLite stays.

SQLite is a good fit for the first hosted form if each workspace gets its own database, WAL mode is used carefully, backups are disciplined, and writes are serialized where needed.

Postgres is not required for the first SaaS.

A control-plane SQLite database plus per-workspace SQLite databases can serve 1-9 users while preserving a clean migration path later.

Do not use one shared global data directory.

The current data/ model is excellent locally but unsafe for hosted SaaS unless it becomes workspace-scoped and impossible to accidentally cross-read.

3. Data Model

The most important refactor is not storage technology. It is introducing explicit identity, tenancy, and workspace boundaries everywhere.

Core Schema
Object Purpose Where It Lives First Notes
User Login identity for a person. control.db Email, password hash or provider id, MFA status, status, created/last login timestamps.
Organization A household now; an advisor firm later. control.db Use org_type = household | advisor_firm. Do this now even if every org starts as a household.
Membership Connects users to organizations. control.db Roles: owner, member, advisor, admin, read_only. First release can expose only owner.
Workspace The financial data boundary. control.db registry plus workspace SQLite file Each workspace has a path, encryption metadata, backup policy, lifecycle status, and owning org.
Workspace Data Portfolio, profile, plans, recommendations, conversations, context registry. workspaces/{workspace_id}/buildwealth.db Migrate current JSON stores into tables or a hybrid document-table model.
Secrets LLM keys, market-data keys, aggregation tokens. Encrypted store or KMS-backed field encryption Never store plaintext API keys in SaaS. Current plaintext settings are acceptable only for local single-user mode.
Audit Event Security, data mutation, billing, support, and advisor access trail. control.db and optionally workspace DB Record actor, org, workspace, action, timestamp, IP/session, target, and outcome.

4. Security And Privacy Baseline

Hosted financial software must assume users will enter sensitive household data. The SaaS transition should make privacy a core product feature, not a paragraph in the footer.

Launch Gate

Authentication

Add email login, secure password storage or hosted auth, session cookies, CSRF protection, password reset, optional MFA, and account lockout/rate limiting.

Authorization

Every API route must resolve a RequestContext containing user, org, role, workspace, and permissions before touching financial data.

Encryption

Use encrypted volumes at minimum. Prefer per-workspace database encryption or field-level encryption for secrets and especially sensitive records.

Backups

Create tenant-scoped encrypted backups with restore tests. A backup restore must never overwrite or expose another workspace.

Data Rights

Users need export, deletion, account closure, and retention controls. Build these early while the storage model is still flexible.

Compliance Review

Review financial-advice positioning, privacy disclosures, customer-information safeguards, and market-data licensing before inviting non-test users.

Important legal note.

This plan is not legal advice. Before public launch, have counsel review whether any recommendations, portfolio guidance, compensation model, or advisor features trigger investment-adviser, privacy, or financial-data obligations.

Reference points to review.

Start with the SEC's investment adviser materials and the FTC Safeguards Rule guidance. See the source links at the end of this document.

Product design mitigation.

Keep user review/apply boundaries, show evidence and assumptions, avoid trade instructions in early B2C messaging, and make simulations visibly educational.

5. Transition Phases

This sequence takes advantage of the fact that BuildWealth is not in production yet. The goal is to break the single-user assumption first, then host it, then polish the business surface.

Execution Plan
0

Define the hosted product boundary

Decide what the first SaaS is allowed to do. The recommended first product is a hosted private workspace for financial organization, planning, modeling, and review.

  • Write product disclaimers and user-facing advice boundaries.
  • Define B2C household onboarding and minimum useful profile.
  • Decide whether users bring their own LLM key or BuildWealth pays provider costs.
  • Freeze the first hosted feature set: Today, Profile, Portfolio, Plan, Inbox, Copilot, Settings.
Exit criteria

There is one crisp hosted MVP promise and a short list of things the product explicitly does not do yet.

1

Introduce identity and request context

Add the SaaS spine while the app still runs locally. This is the refactor that makes every later step possible.

  • Add User, Organization, Membership, and Workspace models.
  • Add auth middleware and route dependencies for RequestContext.
  • Replace module-global stores with request-scoped store factories.
  • Add tests proving user A cannot read, write, restore, search, or chat against user B's workspace.
Exit criteria

The app can run multiple local test workspaces with no shared financial state.

2

Move from path-backed JSON to workspace SQLite

Keep SQLite, but make it an intentional durable store instead of a snapshot artifact. For speed, use a hybrid schema first: normalized core tables plus JSON document columns for evolving payloads.

  • Create buildwealth.db per workspace.
  • Migrate portfolio, profile, plans, recommendations, conversations, and context registry.
  • Keep import files, reports, and large artifacts in tenant-scoped object/file storage.
  • Add migrations with forward-only versioning and restore drills.
Exit criteria

New workspaces use SQLite as the source of truth. Legacy local JSON import remains available.

3

Host the private beta

Deploy a single small server or VM with managed backups, HTTPS, monitoring, and a clear admin runbook. Do not overbuild the platform yet.

  • Use HTTPS, secure cookies, environment secrets, and isolated workspace directories.
  • Add basic admin tooling: invite user, disable user, inspect workspace health, trigger backup.
  • Add telemetry for latency, errors, job failures, backup freshness, and storage growth.
  • Run with 1-3 friendly users before expanding to 9.
Exit criteria

Real people can use it from the internet, but access is still invite-only and operationally watched.

4

Add billing and entitlements

Billing should arrive after the private workspace model is safe. Do not let billing concerns distort the data architecture too early.

  • Add subscription status, plan tier, trial end, cancellation, invoice status, and webhook processing.
  • Gate costly features: LLM calls, research providers, aggregation syncs, and advisor seats.
  • Add a usage ledger so provider costs are visible per workspace.
  • Keep a manual comp/free plan for early testers.
Exit criteria

The app can charge users without manual bookkeeping and without exposing payment internals to workspace data.

5

Improve ingestion and recurring operation

Once users rely on the product, data freshness becomes the product. Add import flows and scheduled jobs with strong visibility.

  • Keep CSV/manual import, but add provider abstraction for bank and brokerage aggregation later.
  • Add scheduled price updates, stale-data warnings, and sync health per workspace.
  • Add background job records with retries, failure reasons, and user-visible status.
  • Add export packages so users can leave with their data.
Exit criteria

A user can trust that BuildWealth tells them when data is missing, stale, or degraded.

6

Prepare for advisors without becoming advisor-first

Add the minimum primitives that let a financial advisor or small firm use the platform later: client workspaces, role-based access, consent, and audit trails.

  • Add org type advisor_firm behind a feature flag.
  • Add client workspace ownership and advisor membership with scoped permissions.
  • Add client consent records and advisor access audit views.
  • Keep advisor features separate from consumer onboarding and pricing.
Exit criteria

The data model supports advisor use, even if the public product remains B2C.

6. Exact Codebase Change Areas

These are the specific places where the current single-user app needs to change. The sequence matters: introduce boundaries before adding more features.

Implementation Map
Area Current Shape SaaS Change First Acceptance Test
main.py Global stores are created from global settings paths. Create route dependencies that resolve RequestContext and workspace-scoped stores. Two authenticated users calling the same endpoint receive different portfolio/profile data.
settings.py Single app settings include global data paths. Split app config from workspace config. Add control-plane DB path and workspace root path. Changing workspace id changes storage roots without changing process env.
Storage services Read and write local JSON files under data/. Add SQLite repositories per domain, with migration adapters from current JSON payloads. Round-trip current fixtures into SQLite and back through existing API response models.
UserSettingsStore Stores API keys in plaintext for local single-user mode. Replace with encrypted workspace secrets and masked API responses. Raw database inspection cannot reveal stored LLM API keys.
Backup/restore Backs up local data roots. Back up one workspace at a time and require authorization to restore it. User A cannot list, restore, or infer the existence of user B backups.
Copilot/context Assembles context from global app stores. Context assembler accepts workspace repositories only. Add tenant id to traces and cache keys. Conversation and context caches cannot cross workspace boundaries.
Frontend API helper Calls relative /api/... endpoints with no auth concerns. Add session handling, login/logout, workspace selection, 401/403 flows, and CSRF handling if cookie-based. Expired session returns user to login without losing unsaved draft where practical.
Tests Mostly single-user behavioral tests. Add isolation, authorization, migration, backup, and hosted smoke tests. A dedicated test suite fails if any route can access data without a workspace context.
First refactor: add RequestContext and store factories.
Second refactor: make every route workspace-aware.
Third refactor: replace plaintext settings with encrypted secrets.
Fourth refactor: migrate workspace data to SQLite source-of-truth.
Fifth refactor: add hosted auth and invite-only beta operations.
Sixth refactor: add billing, usage ledgers, and advisor-ready roles.

7. Advisor Path Without Overbuilding

The app should not become advisor software on day one. But the core model should not block that future either.

Expansion

Build Now

  • Organizations and memberships, even if hidden from the UI.
  • Workspace ownership separate from user identity.
  • Role enum that can grow beyond owner/member.
  • Audit events for all sensitive reads and writes.
  • Clear consent model for sharing a workspace.

Defer

  • Advisor firm dashboard.
  • Client CRM.
  • Compliance archiving and supervisory review tools.
  • Multi-advisor team assignment.
  • Advisor-specific billing and contracts.

8. Main Risks

These are the risks most likely to derail the SaaS transition if handled late.

Watch List
Risk Why It Matters Mitigation
Accidental cross-tenant data access This is the cardinal hosted-app failure for financial software. Workspace-scoped store factories, authorization dependencies, and isolation tests for every domain.
Plaintext secrets Current local settings are explicitly not SaaS-safe. Encrypted secrets before any hosted user enters API keys or provider tokens.
Regulatory ambiguity Recommendations, trade simulations, and compensation can change the legal posture. Legal review, careful copy, review/apply UX, and product boundaries before public launch.
SQLite operational mistakes SQLite is capable, but it needs disciplined connection, backup, and write handling. Per-workspace DBs, WAL mode, serialized writes where needed, tested backups, and integrity checks.
Provider cost surprises LLM, market-data, and aggregation calls can become the real unit economics. Usage ledger, quotas, caching, plan limits, and bring-your-own-key option for early users.
Overbuilding for firms too early Advisor workflows can swamp the B2C product. Put advisor primitives in the data model, but keep advisor UI behind a later feature flag.

9. Questions To Answer Next

These are the few decisions worth making before implementation. Everything else can be discovered while building the first workspace-aware slice.

Open Items
Auth strategy

Do you want self-hosted auth in FastAPI, or do you want a hosted auth provider for the first beta?

LLM cost model

Should early users bring their own API keys, should BuildWealth pay for calls, or should both modes exist?

Encryption standard

Is encrypted disk plus encrypted secrets enough for beta, or do you want encrypted SQLite files from the start?

Data ingestion

Should beta users start with manual/CSV entry only, or is brokerage/bank aggregation required for the first useful version?

Advice boundary

How conservative should the product be with investment recommendations in the public B2C version?

Deployment target

Do you want the first 1-9 users on one small VPS, a home/private server, or a managed app host?
